# Рабочее размещение COND

Комплект подготовлен для одного постоянно работающего Linux-сервера с Docker Compose. Это обычный рабочий сервер: он принимает приходы, выпуски, заявки и выплаты. Телефон хранит очередь без связи и отправляет её в эту же базу после подключения. Дополнительный режим SYNC_ROLE=cloud — только внешняя копия для просмотра, он здесь не включён.

## Что требуется от владельца размещения

Реальные домен, сервер, почтовый аккаунт SMTP и сильные пароли. DNS домена должен указывать на сервер, порты 80 и 443 должны быть доступны. PostgreSQL и API не публикуются наружу. В комплекте нет рабочего домена, оплаченного сервера и почтовых реквизитов; они не подключались.

## Первый запуск

Команды выполняются в папке deploy на сервере. Не копируйте локальный .env, node_modules или демонстрационную базу в рабочую среду.

1. Скопировать `.env.production.example` в `.env.production`, установить права `chmod 600 .env.production` и заполнить значения. SECRET_KEY сгенерировать случайным, минимум 48 символов. Пароли владельца PostgreSQL, пользователя приложения и администратора должны различаться. Шаблон содержит заглушки, с которыми запуск запрещён проверкой настроек.
2. Проверить конфигурацию: `docker compose --env-file .env.production -f compose.yml config --quiet`.
3. Для новой пустой базы: `docker compose --env-file .env.production -f compose.yml up -d --build`.
4. Для переноса существующей базы: сначала получить полноценный pg_dump старой базы, проверить восстановление на отдельной базе. Затем запустить только `db`: `docker compose --env-file .env.production -f compose.yml up -d db`. После готовности PostgreSQL выполнить `sh import-empty.sh /absolute/path/source.dump`. Скрипт откажется работать, если в целевой базе уже есть таблицы; он ничего не удаляет. После импорта запустить остальные службы командой из шага 3. Перенести также старые изображения, если они используются. Исходная рабочая база клиента в этой задаче не предоставлена и не импортировалась.
5. Проверить службы: `docker compose --env-file .env.production -f compose.yml ps`, затем `docker compose --env-file .env.production -f compose.yml exec -T backend node scripts/check-production.js`. Проверка проверяет настройки, соединение с PostgreSQL, отсутствие демонстрационных аккаунтов, наличие администратора, права обычного пользователя БД и SMTP-авторизацию. Письмо при этой проверке не отправляется.
6. Открыть HTTPS-адрес, войти администратором с SUPERADMIN_EMAILS и SUPERADMIN_PASSWORD, получить код по почте. Начальный пароль создаётся только для нового аккаунта; смена значения в .env не меняет пароль существующего администратора.

Caddy получает и обновляет HTTPS-сертификат. Приложение запускается без демонстрационных аккаунтов; API работает от пользователя node, пользователь БД cond_app не имеет полномочий superuser. Данные PostgreSQL, изображения и сертификаты хранятся в отдельных постоянных Docker volumes. `restart: unless-stopped` возвращает службы после перезапуска. Проверка здоровья API обращается к базе. Docker должен быть включён в автозапуск ОС. Автоматическое восстановление повреждённых данных и удалённый мониторинг в комплект не входят.

## Доступы и путь заявки

Администратор: Настройки → имя, email, пароль, роль «Представитель фирмы», фирма → «Создать доступ». Реквизиты нужно передать человеку отдельно; приложение не рассылает пароли. Представитель входит по той же HTTPS-ссылке, затем подтверждает вход кодом из письма. В его кабинете есть только свободная готовая продукция и его собственные заявки/накладные.

Представитель выбирает кг товаров, дату и комментарий → «Отправить заявку». Фирма берётся из назначенного профиля, подменить её в запросе нельзя. Принятая сервером заявка резервирует товар. У администратора на главной увеличивается число новых заявок. Администратор открывает заявки, согласует цены за кг, затем подтверждает отгрузку. При отгрузке списывается готовая продукция и появляется продажа. Накладную можно открыть и распечатать/сохранить PDF. До отгрузки это проект внутреннего складского документа; бухгалтерский формат с реквизитами требует отдельной настройки.

Представитель не может назначать цены согласования, подтверждать отгрузку, видеть чужие заявки, материалы, себестоимость, финансы, зарплаты или создавать пользователей. Он может отменить свою неотгруженную заявку — резерв освобождается. У каждого представителя свои заявки; принадлежность одной фирме автоматически не открывает ему заявки другого аккаунта.

Работник: видит каталог названий для выпуска, свою выработку, свои начисления и выплаты. Записывает фактические кг и может отменить свой непроведённый выпуск. Не проводит списание сырья, не меняет рецептуры, не назначает зарплату и не видит себестоимость. Проведение выполняет администратор.

Администратор видит все текущие данные, проводит выпуск и отгрузки, записывает приходы/выплаты, заводит доступы. «Закрыть доступ» отзывает все сеансы выбранного сотрудника/представителя; история не удаляется. Открытие доступа требует нового входа. У аккаунта могут одновременно работать телефон и ноутбук, до 10 сеансов. Выход закрывает только текущий сеанс. Роль и действительность сеанса проверяются по базе на каждом запросе; старый токен не сохраняет прежние права. Старые разделы доступны только администратору и только для просмотра. Журнал успешных изменений хранит автора, время и вид операции, без паролей.

Офлайн-телефон может показывать уже загруженную копию и создавать локальные записи. Нельзя удалённо стереть эту копию без связи. Закрытый на сервере аккаунт не сможет загрузить новые данные или провести накопленные операции.

## Приёмка перед реальными операциями

Проверить реальные Android/iPhone и ноутбук: вход и доставку кода; приход, рецептуру, выпуск, списание и зарплату; заявку представителя и отказ в доступе к лишним разделам; согласование/отгрузку и печать; закрытие доступа. В Настройках выполнить «Проверить, всё ли сходится».

Для офлайн-проверки один раз загрузить приложение по HTTPS, установить на главный экран, включить авиарежим и повторно открыть. Записать выпуск/приход, закрыть и открыть, убедиться в наличии очереди. Включить связь, открыть приложение и проверить однократное принятие записей. Остатки офлайн предварительные; отказ сервера остаётся в очереди с причиной. Фоновая отправка из полностью закрытого приложения не реализована — откройте его при связи.

## Резервные копии и обновления

`sh backup.sh` создаёт PostgreSQL dump и архив изображений в deploy/backups. Файлы содержат рабочие данные; хранить с ограниченным доступом и копировать на отдельный носитель/защищённое хранилище. Не публиковать вместе с сайтом. Секреты .env хранить отдельно. Расписание, хранение вне сервера и срок хранения оператор настраивает отдельно; скрипт сам не является автоматическим резервным копированием.

`sh restore-test.sh backups/cond-ДАТА.dump` восстанавливает dump в новую изолированную базу cond_restore_ДАТА, не заменяя cond_prod. Скрипт проверяет восстановление и выводит контрольные количества. Проверить записи и приложения в восстановленной базе отдельно; проверочную базу не удаляет. Для полного восстановления нужны также архив изображений и настройки сервера.

Перед обновлением выполнить и проверить копию, затем `docker compose --env-file .env.production -f compose.yml up -d --build`. Запуск создаёт недостающие таблицы и применяет ограниченные совместимые изменения количественных полей; sync({alter:true}) не применяется. Старые миграции и демо-данные не запускаются на новой рабочей базе как сброс. Деструктивный откат миграций не выполняется автоматически.

## Что проверено здесь

Автоматические сценарии учёта/прав и доставки копии проходят в отдельных локальных PostgreSQL-базах; production-сборка интерфейса проходит. Docker Compose разобрал конфигурацию без ошибок; bash проверил синтаксис скриптов. Небезопасные production-настройки отклоняются.

Docker Engine на этом компьютере недоступен, поэтому сборка/запуск контейнеров, Caddy/HTTPS, создание пользователя БД init-скриптом и backup/restore-скрипты в контейнерах ещё не проверены. Реальные SMTP, телефоны и исходная рабочая база клиента также требуют приёмки. Это подготовленный комплект размещения, а не подтверждение уже запущенного продакшена. Прямая интеграция с 1С требует адаптера под выбранную конфигурацию; сейчас есть JSON-выгрузка.

Дополнительно backend реально запускался в production-режиме в изолированной локальной PostgreSQL-базе с отдельной ролью без superuser. Семь проверок подтвердили старт, отсутствие демо-данных и демо-входа, сохранение администратора при перезапуске и отказ при добавлении демо-аккаунта. Это проверка приложения с PostgreSQL, не проверка контейнерного init-скрипта. SMTP-письма не отправлялись.
